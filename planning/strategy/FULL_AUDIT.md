# NeuroLoad — Comprehensive Codebase & Product Audit

**Date:** 2026-03-07  
**Auditor:** Product Owner / Senior Review  
**Scope:** Full codebase review — all Dart source files, pubspec, planning documents, architecture, data layer, UX flows, security, performance, and product-readiness  
**Method:** Line-by-line source reading of every file in `lib/`, `pubspec.yaml`, and all planning documents

---

## Executive Summary

NeuroLoad is a well-architected Flutter app with a clean separation of concerns, a thoughtful data model, and several genuinely clever UX decisions (the breathing ring, progressive overload mechanic, distraction-as-data philosophy). The codebase is Sprint 4 complete and structurally ready for beta testing. However, a cluster of bugs discovered in this audit — some of which are pre-existing (logged) and some new — would cause poor first impressions in a live beta if left unresolved. There are also architectural choices that will create compounding technical debt in Phase 2 if not addressed now.

This document organises findings into five categories: **Critical Bugs** (will cause crashes or data loss), **High Priority Bugs** (will cause user-facing failures), **Medium Priority Issues** (degraded experience), **Architectural Risks** (future debt), and **Product Readiness** (launch-blocking gaps).

## Part 1 — Critical Bugs (Fix Before Beta)

### CRIT-01: Encryption Key Generation Is Deterministic and Weak

**File:** `lib/data/app_database.dart` → `_generateKey()`

**Code:**
```dart
String _generateKey() {
  final rand = List.generate(32, (_) {
    const chars = '0123456789abcdef';
    return chars[(DateTime.now().microsecondsSinceEpoch * 1337) % chars.length];
  });
  return rand.join();
}
```

**Problem:** This is not random. `DateTime.now().microsecondsSinceEpoch` is essentially the same value for all 32 iterations of the loop because the loop executes in microseconds and the timestamp does not advance between iterations. The result is a 32-character string where all characters are identical or near-identical. On most devices this generates something like `"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"`. The encryption is effectively broken — any attacker with the algorithm can reconstruct the key.

**Impact:** The entire security promise of NeuroLoad ("your data is encrypted on-device") is false for any user whose key was generated by this function. This is a data-security vulnerability, not just a bug.

**Fix:** Use Dart's `dart:math` `Random.secure()` to generate genuinely cryptographically random bytes:
```dart
import 'dart:math';
String _generateKey() {
  final rng = Random.secure();
  return List.generate(32, (_) {
    const chars = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';
    return chars[rng.nextInt(chars.length)];
  }).join();
}
```
For existing users whose keys were generated by the broken function, there is no migration path — their databases were encrypted with a weak key. New installs after the fix will have strong keys. Document this in release notes if the fix ships after any public beta.

### CRIT-02: Router `redirect` Uses `async` in a Context That Does Not Support It Safely

**File:** `lib/router.dart` → `routerProvider` → `redirect` callback

**Code:**
```dart
redirect: (context, state) async {
  final prefs = await SharedPreferences.getInstance();
  ...
}
```

**Problem:** `GoRouter`'s `redirect` function is called synchronously during navigation. Making it `async` causes the redirect to be evaluated on a `Future`, which means the router emits `null` (no redirect) on the first call while the `Future` is pending, then the redirect fires after the navigation has already completed. The practical effect: the onboarding guard and paywall gate work on second navigation but not reliably on the first deep link or app launch. Users who have not completed onboarding may briefly see the Setup screen before being redirected to Onboarding.

**Fix:** Read shared preferences state from Riverpod providers (which are already loaded in memory) instead of calling `SharedPreferences.getInstance()` in the redirect. The `isPaidProvider` and `freeSessionsUsedProvider` already exist and are synchronous:

```dart
redirect: (context, state) {
  final hasOnboarded = ref.read(/* onboarding provider */);
  final isPaid = ref.read(isPaidProvider);
  final used = ref.read(freeSessionsUsedProvider);
  ...
}
```
Add a dedicated `hasOnboardedProvider` backed by `SharedPreferences` that loads on app start (similar to `isPaidProvider`), so the redirect can read synchronously from in-memory state.

### CRIT-03: `AppDatabase` Uses `forTesting` Constructor in Production

**File:** `lib/data/app_database.dart`

```dart
static Future<AppDatabase> initialize() async {
  ...
  _instance = AppDatabase.forTesting(executor);  // ← named "forTesting"
  return _instance!;
}
```

**Problem:** The production database singleton is created using a constructor explicitly named `forTesting`. While this likely works functionally (Drift's test constructor and production constructor both accept a `QueryExecutor`), it is a semantic confusion that could cause a real issue: if the `forTesting` constructor ever has different behaviour (e.g., skipping migrations, using in-memory storage in a test environment) this will silently affect production. It also signals to any future contributor that this is a test database.

**Fix:** Rename `AppDatabase.forTesting` to `AppDatabase._internal` or `AppDatabase(executor)` and keep a separate `AppDatabase.forTesting(executor)` that explicitly uses an in-memory executor for tests.

### CRIT-04: Session Can Be Started While Another Is Already Active

**File:** `lib/providers/session_provider.dart` → `SessionNotifier.startSession()`

**Problem:** `startSession()` does not check `state.phase` before proceeding. If called twice (e.g., if the face-down sensor fires and the user also taps the START button simultaneously), two DB rows are inserted and the in-memory state is overwritten with the second call, orphaning the first session's DB row with `isCompleted = false`. This creates an unrecoverable zombie session that will trigger the zombie recovery UI on the next launch, even though the user never had a real session.

**Fix:**
```dart
Future<void> startSession() async {
  if (state.phase == SessionPhase.active) return; // guard
  ...
}
```

## Part 2 — High Priority Bugs (Fix Before Public Launch)

### HIGH-01: Settings Are Dual-Stored (SharedPreferences AND AppSettings Table) With No Sync Between Them

**Files:** `lib/providers/session_provider.dart` → `SettingsNotifier`, `lib/data/tables.dart` → `AppSettings`

**Problem:** The database has an `AppSettings` table (with columns for `highContrast`, `fontFamily`, `cloudSyncEnabled`, `localOnlyNotes`, `hasCompletedOnboarding`, `totalSessionCount`). The `SettingsNotifier` also reads/writes the same settings to `SharedPreferences`. These two stores are never synced. The `AppSettings` table is declared but appears to never be written to by `SettingsNotifier`. This means:
- The `AppSettings` table is dead code in the current implementation.
- `hasCompletedOnboarding` is stored in `SharedPreferences` (key: `has_completed_onboarding`) but the DB has a column for it too — they can diverge.
- `totalSessionCount` in the DB table is never incremented anywhere in the code.
- When the user taps "Wipe All Data", `SharedPreferences.clear()` is called — this wipes settings. But the `AppSettings` DB row is NOT cleared (only `sessions` and `laps` are deleted). Post-wipe, the DB table thinks settings have values but SharedPreferences is empty.

**Fix:** Choose one source of truth. The simplest fix for MVP is to delete the `AppSettings` table entirely (it adds complexity without benefit). Settings live in `SharedPreferences` only. Update `schemaVersion` to 2 and add a migration that drops the `app_settings` table. Long-term (Phase 2), consider moving settings to the DB for cloud sync, but make it the single store, not a duplicate.

### HIGH-02: `_generateKey()` in `app_database.dart` Uses Only 16 Hex Characters (4-bit entropy per char)

*(This compounds CRIT-01 above — noted separately as a second dimension of the same vulnerability.)*

The character set is `'0123456789abcdef'` — only 16 characters. With 32 characters and 16 options, the keyspace is 16^32 = 2^128, which would be fine if the selection were random. But because it is not random (see CRIT-01), the actual keyspace is near zero. The fix in CRIT-01 addresses both dimensions.

---

### HIGH-03: Onboarding Completion Is Written to SharedPreferences But Router Reads It Asynchronously on Every Navigation

*(Extends CRIT-02)* Every navigation event triggers `SharedPreferences.getInstance()` in the router redirect. On a cold start with many SharedPreferences reads in flight simultaneously (database init, settings load, subscription load, router redirect), there is a race condition where the router fires before SharedPreferences has loaded, resulting in a brief redirect to `/onboarding` for users who have already completed it.

**Symptoms:** Users with the app installed who update to a new version occasionally see the onboarding screen flash briefly before being redirected to `/setup`. This has been reported in similar GoRouter + SharedPreferences patterns.

### HIGH-04: `focusDensity` in `_BaselineTestPage` Is Capped at 1.0 Before Division, Not After

**File:** `lib/screens/onboarding/onboarding_screen.dart` → `_BaselineTestPageState._finish()`

```dart
final focusDensity = (_lapCount == 0
    ? 1.0
    : (elapsed - _lapCount * 30.0).clamp(0.0, elapsed.toDouble()) /
        elapsed);
```

**Problem:** If `elapsed` is 0 (user skips baseline immediately after starting), this performs division by zero. `elapsed` is `_totalSeconds - _remaining.clamp(0, _totalSeconds)`. If `_finish()` is called when `_remaining == _totalSeconds` (immediately), `elapsed = 0`, and `(elapsed - ...) / elapsed` is `0/0 = NaN`. The NaN is then written to the DB as `focusDensity` for the baseline session.

**Fix:**
```dart
final focusDensity = elapsed == 0
    ? 1.0
    : (_lapCount == 0
        ? 1.0
        : (elapsed - _lapCount * 30.0).clamp(0.0, elapsed.toDouble()) / elapsed);
```

### HIGH-05: `router.dart` Paywall Gate Checks `SharedPreferences` Directly Instead of `paywallGateProvider`

**File:** `lib/router.dart`

```dart
final isPaid = prefs.getBool('subscription_is_paid') ?? false;
final used = prefs.getInt('subscription_free_sessions_used') ?? 0;
```

`paywallGateProvider` already exists in `subscription_provider.dart` and computes this exact logic. The router duplicates it using raw SharedPreferences reads that may be stale. If `SubscriptionNotifier.markPaid()` updates the in-memory state but the router has already cached a `prefs` instance, the paywall gate may not lift immediately after purchase. The user pays but still sees the paywall until the next cold start.

**Fix:** Use `ref.read(paywallGateProvider)` in the router redirect instead of reading SharedPreferences directly.

### HIGH-06: `FaceDownNotifier` Never Resets `state` to `false` After It Is Consumed

**File:** `lib/providers/sensor_provider.dart` → `FaceDownNotifier`

The `consume()` method exists and sets `state = false`. It is called from `SetupScreen` via `ref.listen(faceDownStartProvider, ...)`. However, if the user navigates away from `SetupScreen` while `faceDownStartProvider` is `true` (e.g., by pressing the back button), the state stays `true`. On next visit to `SetupScreen`, the listener fires immediately with `next == true` and the session starts automatically without user intent.

**Fix:** Call `consume()` in `SetupScreen.dispose()` to ensure the state is always cleared when leaving the screen.

### HIGH-07: Lap Duration for Auto-Distraction (`sensor_provider.dart`) Uses Unadjusted Wall-Clock Time

**File:** `lib/providers/sensor_provider.dart` → `_onEvent()`

When `addLap()` is called from the sensor (auto phone flip), the `lapDurationSeconds` in `SessionNotifier.addLap()` is computed as `DateTime.now().difference(prevLapTime).inSeconds`. This is correct. But the auto-log happens with `trigger: DistractionTrigger.phone, note: 'auto: phone flipped up'` — if the oversensitivity bug (BUG-14) fires multiple times, each duplicate lap also computes a `lapDurationSeconds` of ~0 (because `DateTime.now()` is the same moment for all of them). This pollutes the `sessionOneRM` computation: the algorithm looks for the maximum interval between consecutive lap timestamps, and duplicate timestamps with 0-second gaps between them will always produce a `sessionOneRM` of 0 for that slot. The all-time 1RM display on the dashboard could show 0 after a session affected by the oversensitivity bug.

This is resolved by BUG-14 fix (debounce), but the data already written to the DB for past sessions is corrupt. Consider adding a data-repair migration on schema upgrade.

### HIGH-08: `SummaryScreen` Resets Session Before Navigation, Losing State If Navigation Fails

**File:** `lib/screens/summary/summary_screen.dart`

```dart
onPressed: () {
  final earned = session.earnedBreakDuration;
  ref.read(sessionProvider.notifier).resetSession();  // ← state wiped
  context.go('/break', extra: earned);                // ← navigate
},
```

If `context.go('/break', ...)` fails for any reason (route not found, widget unmounted), the session state has already been destroyed. The user loses their session summary data permanently. The correct order is navigate first, then reset session in the destination screen's `initState` or after confirming navigation succeeded.

## Part 3 — Medium Priority Issues

### MED-01: `_AppDatabase.AppSettings` Table Has a `totalSessionCount` Column That Is Never Updated

**File:** `lib/data/tables.dart`

```dart
IntColumn get totalSessionCount => integer().withDefault(const Constant(0))();
```

This column is never read from or written to anywhere in the codebase. It is dead schema. Delete it or implement it (the `FreeSessionsNotifier` in `subscription_provider.dart` already tracks session count in SharedPreferences — consolidate).

### MED-02: `CoachEngine` Compares by Object Identity, Not Value

**File:** `lib/providers/coach_provider.dart` → `generateInsights()`

```dart
if (latestOneRm == allTimeOneRmSeconds && latestOneRm > 0) {
```

This compares integer values, which is fine for `int`. However the logic has a subtle flaw: if the user has two sessions with the same 1RM (e.g., both at 45 minutes), the "New Personal Best" insight fires for both sessions — including the second one, which merely *matched* the record, not beat it. The insight says "🏆 New All-Time 1RM!" but the user did not improve.

**Fix:** Track the *previous* all-time 1RM and only fire when `latestOneRm > previousAllTimeOneRm`.

---

### MED-03: `_ClockRingPainter.shouldRepaint` Compares List by Reference

**File:** `lib/screens/dashboard/dashboard_screen.dart`

```dart
@override
bool shouldRepaint(_ClockRingPainter old) =>
    old.hourMinutes != hourMinutes || old.maxMins != maxMins;
```

`hourMinutes` is a `List<double>`. In Dart, `!=` on lists compares by reference, not value. Two different list objects with identical contents are `!=`. This means `shouldRepaint` will return `true` on every widget rebuild even if the data has not changed, forcing an unnecessary repaint of the clock ring on every frame during animation. On low-end devices this causes jank.

**Fix:** Use `listEquals(old.hourMinutes, hourMinutes)` from `flutter/foundation.dart`.

---

### MED-04: `OnboardingScreen` Typewriter Timer Fires 18ms Between Characters on a Full 1,400+ Character String

**File:** `lib/screens/onboarding/onboarding_screen.dart` → `_startTypewriter()`

```dart
_typewriterTimer = Timer.periodic(const Duration(milliseconds: 18), (t) {
  setState(() { _typewriterText = _manifestoFull.substring(0, index + 1); });
  ...
});
```

`_manifestoFull` is approximately 780 characters long. At 18ms per character, the full typewriter effect takes ~14 seconds. Each tick calls `setState()` which triggers a full widget rebuild of `OnboardingScreen` — a `StatefulWidget` with a `PageView`, `AnimationController`, and `ScrollController`. On mid-range Android devices, ~55 rebuild calls per second for 14 seconds is a meaningful battery drain and may cause visual stutter on the manifesto scroll.

**Fix:** Move the typewriter to a dedicated `StatefulWidget` so only the text widget rebuilds on each tick, not the entire `OnboardingScreen`. Alternatively, increase the interval to 22ms (still feels fast) and use a `ValueNotifier` + `ValueListenableBuilder` to scope rebuilds to the `Text` widget only.

### MED-05: `_BaselineTestPage` Writes a DB Session Row With `category: 'baseline'`

**File:** `lib/screens/onboarding/onboarding_screen.dart` → `_BaselineTestPageState._begin()`

```dart
_sessionId = await dao.insertSession(
  SessionsCompanion.insert(
    startedAt: _startedAtMs,
    category: 'baseline',  // ← not a valid PrimaryCategory enum value
    ...
  ),
);
```

`PrimaryCategory` enum values are: `study`, `work`, `creative`, `admin`, `lifestyle`. `'baseline'` is not one of them. This is fine for the DB (it stores strings), but:
1. The Dashboard's category filter will show baseline sessions mixed into the "All" view.
2. Any code that does `PrimaryCategory.values.firstWhere((c) => c.name == session.category)` (e.g., `resumeZombieSession`) will throw a `StateError: No element` when encountering a baseline session.
3. The Coach engine processes baseline sessions alongside real sessions, skewing the "Next Aim" calculation.

**Fix:** Either mark baseline sessions as `isCompleted = false` after the onboarding completes (so they never appear in analytics), or add a `isBaseline` boolean column to the `Sessions` table and exclude them from all dashboard queries.

### MED-06: `BreakTimerScreen` Is Declared in `lib/screens/summary/` but Registered in `router.dart` as `/break`

**File:** `lib/screens/summary/break_timer_screen.dart` + `lib/router.dart`

The break screen lives in the `summary/` directory but is routed outside the `ShellRoute` (without the app shell / navigation bar). This is architecturally correct (break screen should be full-screen), but the file location is misleading. Minor — rename directory or move to `lib/screens/break/`.

### MED-07: `ExportService` Does Not Handle the Case Where `sessions` or `laps` Is Empty

**File:** `lib/services/export_service.dart`

If `sessions` is empty, `_buildSessionsCsv` writes only the header row. This creates a CSV with a single header line. Some CSV parsers treat this as an error. More importantly, `Share.shareXFiles` is called with two potentially empty files. On iOS, sharing empty files can display a confusing empty share sheet.

**Fix:** Check for empty data before calling the export:
```dart
if (sessions.isEmpty) {
  // Show a snackbar: "No completed sessions to export yet."
  return;
}
```

### MED-08: `triggerCountMapFiltered` in `LapDao` Accepts `null` for "All Sessions" but `triggerCountMapProvider` in `session_provider.dart` Has a Separate Non-Filtered Code Path

**File:** `lib/data/daos/lap_dao.dart` + `lib/providers/session_provider.dart`

```dart
// session_provider.dart
final triggerCountMapProvider = FutureProvider<Map<String, int>>((ref) async {
  final cat = ref.watch(categoryFilterProvider);
  if (cat == null) {
    return ref.watch(lapDaoProvider).triggerCountMap();         // ← calls unfiltered method
  }
  ...
  return ref.watch(lapDaoProvider).triggerCountMapFiltered(ids);
});
```

`LapDao.triggerCountMapFiltered(null)` would do the same thing as `triggerCountMap()`, but the provider doesn't use it — it has a branch that calls the unfiltered method directly. This is harmless but creates two code paths that do the same thing. If `triggerCountMap()` is ever modified (e.g., to add a sort), `triggerCountMapFiltered(null)` won't get the update. Consolidate to one method.

### MED-09: `PendingSessionStore` Can Only Queue One Session at a Time

**File:** `lib/services/pending_session_store.dart`

The store uses a single key (`pending_session`). If `finishSession` fails twice (e.g., two sessions in a row with DB errors), the second failure overwrites the first. The first session's data is permanently lost. While DB errors should be rare, the comment says "only the most recent failed session is queued" — this is acknowledged but should be a logged warning, not silent overwrite.

### MED-10: `_manifestoScrollController` Unlock Logic Has a Race Condition with the Typewriter Effect

**File:** `lib/screens/onboarding/onboarding_screen.dart`

The "scroll to accept" gate requires the user to scroll to the bottom of the manifesto. But the manifesto text is being typed out character-by-character. If a fast-scrolling user scrolls to the bottom before the typewriter finishes rendering the full text, the `_manifestoScrollController.position.maxScrollExtent` at that point is smaller than the final `maxScrollExtent`. The scroll listener fires (`pixels >= maxScrollExtent - 10`) when the user reaches the bottom of the *partially typed* text, not the full manifesto. This means the "Continue" button unlocks before the user has seen the full text.

**Fix:** Only allow scroll-to-unlock once the typewriter timer is complete (`_typewriterTimer == null || !_typewriterTimer!.isActive`).

## Part 4 — Architectural Risks

### ARCH-01: `AppDatabase.instance` Is Accessed Directly in `OnboardingScreen`, Bypassing the Riverpod Provider Layer

**Files:** `lib/screens/onboarding/onboarding_screen.dart` → `_BaselineTestPageState._begin()` and `_finish()`

```dart
final dao = AppDatabase.instance.sessionDao;
```

This bypasses `databaseProvider` and `sessionDaoProvider`. If the database initialization order changes, or if a test mocks the database via Riverpod, this direct access will use the real database instead. All database access should go through the provider layer.

---

### ARCH-02: `SessionNotifier` Has 12 Responsibilities

**File:** `lib/providers/session_provider.dart`

`SessionNotifier` handles: session state transitions, DB insertion, DB update (autosave), DB finish, foreground service start/stop, notification show/dismiss, notification callback registration/deregistration, free session counter increment, zombie recovery, lap management, and pending session queue fallback. This violates single-responsibility and makes testing, debugging, and future refactoring extremely difficult. As Phase 2 adds cloud sync, the notifier will become unmanageable.

**Recommendation for Phase 2:** Extract `SessionPersistenceService` (handles all DB and pending queue logic) from `SessionNotifier`. `SessionNotifier` should only manage in-memory state and delegate persistence.

---

### ARCH-03: Settings Split Between DB and SharedPreferences Will Cause Cloud Sync Bugs in Phase 2

**File:** `lib/providers/session_provider.dart` → `SettingsNotifier`, `lib/data/tables.dart` → `AppSettings`

(Extends HIGH-01) When cloud sync is implemented in Phase 2, `SupabaseSyncService` will sync the DB. The `AppSettings` table exists in the DB but is never written to by `SettingsNotifier`. Phase 2 cloud sync will therefore not sync user settings, even though the schema suggests it should. This will surface as "settings not syncing between devices" — a confusing bug to diagnose because the table exists and looks correct.

---

### ARCH-04: `GoRouter` Provider Reads `sessionProvider` via `ref.read` in an Async Context

**File:** `lib/router.dart`

```dart
if (state.uri.path == '/timer') {
  final session = ref.read(sessionProvider);
  ...
}
```

`ref.read` inside a `Provider` factory is fine for one-time reads. But this redirect fires on every navigation event. Because `sessionProvider` is a `StateNotifierProvider`, `ref.read` gets the current snapshot at call time. This is mostly correct, but there is a subtle issue: the `routerProvider` is created once with a `ref` that is the `ProviderContainer`'s ref. If `sessionProvider` is invalidated and recreated (e.g., after a wipe), the `ref` inside the router closure still points to the old container scope. This is low-risk in practice but is technically a violation of Riverpod's use guidelines.

---

### ARCH-05: `ForegroundService` and `NotificationService` Have Overlapping Responsibilities

**Files:** `lib/services/foreground_service.dart`, `lib/services/notification_service.dart`

`ForegroundService` starts and manages a foreground task (Android only) that keeps the timer alive. `NotificationService` shows a separate persistent notification with an "I Got Distracted" action button. These are two different notifications appearing simultaneously on Android: one from `flutter_foreground_task` and one from `flutter_local_notifications`. Users with the app backgrounded will see two NeuroLoad notifications.

The architectural intent may be that they serve different purposes (service keepalive vs. interactive notification), but the overlap should be documented and the user-facing experience cleaned up. Consider using `ForegroundService.updateNotification()` to update the foreground task's own notification text and buttons, eliminating the need for the separate `NotificationService.showSessionActive()` on Android.

---

### ARCH-06: `router.dart` Is a God Object

**File:** `lib/router.dart`

The router handles: onboarding guard, paywall gate, timer route guard, and route definitions for 9+ routes. All in one 100-line `Provider`. As Phase 2 adds more routes (break, cloud settings, B2B dashboard link), this will become increasingly hard to maintain. Extract route guards into separate `RedirectGuard` classes.

---

## Part 5 — Code Quality Issues

### QUAL-01: `withOpacity` vs `withValues` — Mixed Usage

**Files:** `lib/screens/dashboard/dashboard_screen.dart`, `lib/theme/app_theme.dart`, `lib/screens/summary/summary_screen.dart`

The codebase mixes `Color.withOpacity()` (deprecated in Flutter 3.27+) and `Color.withValues(alpha: ...)` (the new API). For example, in `dashboard_screen.dart`:

```dart
// Line using old API:
AppColors.teal.withOpacity(0.9)
// Line using new API in the same file:
AppColors.teal.withValues(alpha: intensity)
```

This will generate deprecation warnings in Flutter 3.27+ and compilation errors in future Flutter versions. Standardise to `withValues(alpha: ...)` throughout. There are approximately 35–40 occurrences of `withOpacity` across the codebase.

### QUAL-03: `lapCount` in `session_dao.dart`'s `finishSession()` Is Redundant With `laps.length`

**File:** `lib/data/daos/session_dao.dart`

For MVP this is acceptable, but in Phase 2 (cloud sync with potential lap deletions), this will cause inconsistency.

## Part 6 — Security Audit

### SEC-01: Encryption Key in `app_database.dart` Is Passed as a Plaintext String in a SQL Pragma

**File:** `lib/data/app_database.dart`

```dart
db.execute("PRAGMA key = '$key'");
```

The key is interpolated directly into a SQL string. If `key` ever contains a single quote character (which is possible given the character set `0-9a-f` — actually not, but after the CRIT-01 fix the character set will be expanded and may include `'`), this will cause a SQL syntax error and the database will fail to open. Additionally, the key value is visible in log output if SQL logging is enabled.

**Fix:** Use parameterised execution if the SQLite binding supports it, or ensure the key character set explicitly excludes single quotes and semicolons. For the fixed key generator using alphanumeric characters, this is safe. But document it.

---

### SEC-02: `SupabaseSyncService` Stores Credentials in `SharedPreferences`

**File:** `lib/screens/settings/settings_screen.dart` → `_showSupabaseConfig()`

The Supabase `projectUrl` and `anonKey` are saved via `service.saveConfig(cfg)`. From context, this saves to `SharedPreferences` (verified in the settings screen). `SharedPreferences` on Android uses an unencrypted XML file. The anon key should be stored in `flutter_secure_storage` (already a dependency) rather than `SharedPreferences`. The anon key is designed to be less sensitive than a secret key, but storing it in an unencrypted file on a rooted device or via adb backup is still a security risk.

---

### SEC-03: `PendingSessionStore` Stores Session KPI Data in `SharedPreferences`

**File:** `lib/services/pending_session_store.dart`

Session data (quality score, focus density, elapsed time) is stored as plaintext JSON in `SharedPreferences` while awaiting a DB retry. This is a minor privacy issue — the DB is encrypted, but the pending queue bypasses the encryption. On Android, `SharedPreferences` is accessible to the app and (on unrooted devices) is not accessible to other apps. But it is not encrypted at rest. Consider using `flutter_secure_storage` for the pending queue, or ensure the pending data is written to the encrypted DB even if the `finishSession` call failed (by writing to a separate `pending_sessions` table in the same encrypted DB).

## Part 7 — Performance Issues

### PERF-01: Dashboard Loads 4 Separate `FutureProvider`s in Sequence, Each Hitting the DB

**File:** `lib/screens/dashboard/dashboard_screen.dart`

The dashboard watches: `completedSessionsProvider`, `sessionCountProvider`, `allTimeOneRmProvider`, `avgFocusDensityProvider`, `triggerCountMapProvider`, `last90DaysProvider`, `coachInsightsProvider`. That is 7 separate async operations, several of which query the full sessions table. On a device with 200+ sessions, this will noticeably delay the dashboard render.

**Recommendation:** Create a single `dashboardSummaryProvider` that batches all these queries into one DB round-trip using a single SQL query with appropriate aggregations. This reduces 7 sequential async renders to 1.

---

### PERF-02: `_CircularHeatmap` Rebuilds Its `CustomPaint` on Every `completedSessionsProvider` Emission

The heatmap recalculates `hourMinutes` and repaints on every stream emission from `watchCompleted()`. During an active session, `watchCompleted()` does not emit because the session is not yet `isCompleted = true`. This is fine during a session. But after a session ends and the data is written, multiple DB events may fire in quick succession (session finish, lap insert batch), each triggering a repaint. Use a `distinct()` operator or debounce on the stream.
